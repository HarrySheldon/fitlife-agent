# FitLife Agent：交互录入、统一计划调整与可验证执行设计

日期：2026-10-10

状态：产品方向已确认；本文具体契约与工程默认值待用户审阅。不是实现完成声明。

代码基线：`1029a27`，工作树 `.worktrees/agent-runtime-refactor`，分支 `codex/agent-runtime-refactor`。

## 1. 目标与边界

面向一般健康成年人，建设能处理模糊输入和多约束修改的 Agent 应用，而不是通用聊天或医疗诊断产品。
核心闭环：理解任务 → 必要澄清 → 工具查询/计算 → 生成候选 → 校验 → 用户确认 → 确定性业务写入。
性能主目标为缩短获得可确认结果的系统处理时间，同时观察用户交互总时长；质量、安全与权限是不可牺牲的约束。

五个模块：交互式录入、统一计划调整、策略与安全、性能优化、评估与对照实验。前四者面向业务，第五者同仓库独立组织，不独立部署。
不新增自由协商的多 Agent 网络，不允许模型直接写数据库，不自动修改营养目标，不承诺医学正确性，不启动真实模型付费评测或生产灰度。

## 2. 已确认产品决策

| 主题 | 决策 |
| --- | --- |
| 服务对象 | 一般健康成年人；超出服务能力的健康请求限制自动建议 |
| 录入范围 | 一次描述整餐、多食物；保留已有训练录入能力，不在第一阶段扩展其多轮能力 |
| 澄清 | 信息充分直接出候选，否则最多两轮；轮数按整次录入，不按食物数量 |
| 估算 | 先提供直观份量选项；仍不明确时允许用户确认有来源的估算，无法合理估算的字段留空 |
| 保存 | 可保存部分已确认食物，剩余项继续保留；重复确认不重复入账 |
| 更正 | 局部更新受影响项；已保存记录必须走单独修改确认 |
| 计划 | 一个协调 Agent，兼容训练和饮食两个领域模块 |
| 跨模块 | 先提示关联，征得同意后才生成另一模块候选 |
| 目标 | 保持已有目标；冲突时解释并询问，不擅自调整 |
| 修订 | 首次生成之后，整次计划调整共享最多两轮内部自动修订；一轮可修两个模块，仅修复不满足约束的部分 |
| 业务范围 | 明显无关请求返回固定说明；含糊/混合请求交 Planner 处理 |
| 混合风险 | 拒绝有害部分，继续可独立处理的正常任务；无法可靠分离时澄清或限制 |
| 隐私 | 按任务和阶段确定必要字段，代码构建输入；不能把完整状态默认发给模型 |
| 恢复 | 退出、刷新、重新登录后恢复草稿与进度，不自动保存或激活；计数不重置 |
| 激活 | 展示差异，确认后创建并激活新版本，保留原版本，仅改变已授权模块 |
| 评估 | 独立场景、执行器、判分和报告；Mock 与 live 分开，真实效果不能用契约测试替代 |

## 4. 架构选择

比较过三种方式：

1. **统一协调流程 + 独立领域模块（采用）**：复用状态、权限、恢复、预算和审计；领域分别负责证据、生成与校验。
2. 一个巨大提示词同时解析、规划、校验：接口少但责任混杂，难以定位失败、隔离数据和控制修改范围，不采用。
3. 多个自主 Agent 互相讨论：增加调用、状态同步和审计成本，当前没有必须采用的需求，不采用。

逻辑关系：业务任务 → 策略判定 → 最小必要上下文 → 领域执行 → 校验/有限修订 → 候选 → 确认事务。
模型输出是建议而非权限；领域工具是确定性函数，不因模块拆分而自动变成独立模型 Agent。

### 4.1 业务任务与 Runtime run 分离

业务任务是持久化交互实例，包含 `task_id/user_id/task_kind/version/status`、授权范围、澄清/修订计数、依赖版本和关联 run IDs。
Runtime run 是一次有限时长执行，不跨用户等待维持连接。一个任务可关联多次 run；run 超时不等于草稿消失。
持久化的是已验证输入、待答问题和候选，而不是模型隐藏推理。所有数据按认证用户读取，不相信模型返回的用户标识。

不立即新建一个万能任务存储：录入扩展现有 SmartEntryDraft；计划增加调整会话对象。共享字段与事件语义，但保留两种领域存储职责。

### 4.2 并发、确认和重放

每次提交回答/更正/确认携带 expected_version 和幂等键。相同键与相同请求返回原结果；同键不同请求拒绝。
后台结果必须通过版本条件写入，不能覆盖用户在模型运行期间作出的修改。重试、刷新不重复扣澄清轮数，不重复执行已成功写入。
确认绑定用户、候选版本、被选条目或计划 patch、依赖版本；确认后内容改变须重新确认。前端 disabled 按钮不是防重机制。

## 5. 子项目一：交互式整餐录入

### 5.1 输入与候选

每项持有稳定 `item_id`、修订号、食物匹配、份量、摄入比例、来源、缺失字段和状态。
来源细化到字段，至少区分 user_provided、catalog、estimated；用户认可估算不把 estimated 改成实测。
估算保存规则/目录版本与假设。目录营养值和代码换算负责数字，不让模型凭空填精确营养值。

### 5.2 状态与澄清

任务状态：collecting / awaiting_clarification / awaiting_confirmation / partially_saved / completed / cancelled / expired。
条目状态：needs_clarification / ready / saved / discarded；估算标记独立于状态。
流程：提取多项 → 匹配目录 → 确定关键缺失项 → 合并提问 → 合并用户回答 → 局部重新计算 → 候选。
每轮是一组已持久化的问题，不是一个 HTTP 请求；重发同组问题不增加轮数。提问前用版本条件原子记录轮数与问题 ID。
达到两轮后系统不再主动发第三轮；允许用户主动补充。可合理估算则展示假设等待确认，否则提供字段留空/手动补充/取消，不伪造可保存状态。
缺少正式记录必填字段时，该项不能保存；不阻塞同餐其他合格条目。

### 5.3 局部更正与部分保存

“牛肉面改牛肉粉，只吃一半”仅使食物匹配、份量与营养计算失效；奶茶项保持不变。
更正会使旧确认失效，依赖这些值的合计重新计算。已保存项不可被更正消息自动覆盖，需转入显式编辑流程。
确认请求指定 ready 条目及其修订号。一次选中集合事务性写入，返回每项正式记录 ID，剩余项留在草稿。
如果任一所选项失效，整次所选集合不写入并返回冲突，避免客户端不知道哪些成功；用户可以重新选择有效子集。
幂等记录必须覆盖 `(user_id, task_id, item_id, revision)` 的已提交映射，不能只依赖整餐的一次性确认键。

### 5.4 前端与验收

同页展示问题组、直观份量选项、候选来源、估算提示、逐项选择和已保存状态。恢复显示更新时间，不自动重放确认。
验收包含多食物、两轮上限、不知道份量、两端同时修改、部分确认重试、已保存项更正、失效目录条目和跨用户草稿访问。

## 6. 子项目二：统一计划调整 Agent

### 6.1 协调与领域职责

协调层提取目标和约束，确定 authorized_domains，必要时追问，调用 training/diet 模块并合并候选。
领域模块统一提供“构建上下文、生成 patch、校验 patch、依据 violations 局部修订”能力；领域校验算法不同。
输出必须包含字段路径、旧值、新值、理由及证据引用。字段白名单限定可改路径，模型不能返回全量对象替换未授权模块。

训练硬约束包括用户确认的可用天数/时间、器械和明确禁止动作；偏好独立记录。时长等计算以工具假设为依据，不把估计解释为实测。
饮食硬约束包括过敏/忌口和既有目标；营养目标容差复用经过审阅的业务规则，不在提示词内临时发明阈值。
健康安全限制始终不可自动放宽。用户目标冲突时请求用户在允许范围内做取舍，不由模型偷偷修改目标。

### 6.2 有限修订与跨模块许可

首次生成不是修订；其后最多两轮自动修订。整任务共享额度已获用户确认，不允许两个模块各修两轮而隐性超额。
例如首次训练、饮食均失败，第一轮同时修两个模块只记一轮；若训练已合格，第二轮只修饮食。此后仍失败则停止自动修订。
联合修订轮可以只调用失败模块，另一模块缓存候选不变；底层传输重试由 Runtime 计费计数，但不冒充新业务修订轮。两轮限制不是两次模型调用，也不是两轮用户追问；调用数、token 与超时另受 Runtime 和任务预算限制。
每轮开始前原子持久化 round_id、轮号及待处理模块；同轮恢复不重复扣额度，已完成模块不重复生成。刷新、断线不能重置额度。
两次后仍失败转 awaiting_user_decision，展示不可满足的约束，不允许激活。刷新、恢复不重置计数。
用户明确改变任务范围或约束后，可创建有前序关联的新候选版本/新调整任务；不能由系统自动创建新任务绕过上限。
训练发现饮食关联时先展示许可请求；拒绝许可则保持饮食不变，原任务可以继续或说明不可行。

### 6.3 生效与冲突

调整会话记录 base_plan_id、基准内容版本/摘要、目标/限制版本及授权范围。
确认前再次验证依赖和 patch；原计划或关键限制变化则返回 stale，展示原因并重新计算，不在后台悄悄换基准。
确认事务原子完成：验证当前基准 → 检查授权和确认 → 创建新版本 → 更新生效指针 → 记录幂等结果。旧版本不可变。
单模块修改也生成完整的新计划版本，但另一模块由代码复制并断言一致。联合调整作为同一候选整体确认，避免只激活一半后失去跨领域一致性；这是本文建议的第一版默认值。
现有 take_draft/save/失败补回模式不能直接视为满足上述跨步骤原子性；实施前需为实际存储 Adapter 明确事务/锁和故障恢复方案。

## 7. 共享恢复与生命周期

建议复用录入草稿现有 30 天到期策略。计划调整会话建议同样保留 30 天，但可激活候选继续遵循现有 30 分钟有效期；过期候选可显示，不能直接激活。
这是待审阅的工程默认值，不是已由用户确定的期限。配置分别表达“会话可恢复时间”和“候选可确认时间”，不能混成一个 TTL。
恢复时读取最新任务版本，检查目录、档案约束和计划依赖；只让受影响计算失效。模型运行中断后不假装继续原进程，检查已提交结果，再按幂等规则启动新 run。
敏感草稿保留是业务功能，不是诊断日志；访问、导出、删除和账户删除应覆盖新任务状态。到期立即拒绝使用，物理清理走显式维护流程，并单独记录清理失败。
等待用户不占用模型请求或工作线程；取消只终止当前操作/任务，不撤销已确认的正式记录。

## 8. 子项目三：策略、安全与隐私

### 8.1 判断分轴，执行统一

Scope：in_scope / out_of_scope / mixed / unclear。
Risk：内容风险及健康能力限制；Injection：指令操纵信号；Capabilities：代码批准的工具与修改范围。
Planner 可以建议分类但不能授予权限，模型置信度不是授权凭据。
明显无关短路采用高精度、保守规则；单个“代码”“股票”词不是拒绝依据。不确定则走 Planner。寒暄和产品帮助归为允许的辅助意图。
混合任务输出保留的正常子任务与受控拒绝理由。下游只接收获准任务；无法独立分离则澄清/限制，避免以“正常部分”为名继续完成有害目标。

### 8.2 数据需求契约

| 调用阶段 | 必要输入 | 不应默认提供 |
| --- | --- | --- |
| 范围/意图 Planner | 当前任务文本、页面类型、指代所需候选摘要 | 完整档案和历史 |
| 饮食录入 | 本餐描述、已确认项、缺失字段、食物匹配、估算来源 | 身体指标、完整健康档案 |
| 训练调整 | 原计划训练片段、时间器械、目标、经验、相关执行摘要与动作限制 | 饮食明细、身份信息、无关健康记录 |
| 饮食调整 | 原饮食片段、确定性计算好的营养目标、过敏忌口、预算与准备时间 | 默认发送目标计算所需的全部身体原始数据 |
| 联合协调 | 获准范围、两边 patch、约束及冲突 | 两模块全量原始数据 |
| 数值校验 | 事实引用、指标/单位/日期/来源 | 姓名、联系方式 |
| 羞辱语义审核 | 必要问题上下文和待发布正文 | 额外完整档案 |
| 权限/确认校验 | 认证身份、版本、确认记录、资源归属 | 不调用模型 |

输入由任务专用 DTO/构建器白名单生成，禁止通用 state.model_dump 直接发送；缺必要字段触发澄清，不自动扩大读取范围。
时间窗由业务请求指定或产品配置给定，并在摘要中标明覆盖期；不能无限加载历史。自由文本可能含用户主动输入的身份信息，必要性过滤也需覆盖自由文本，不能只删除结构化姓名字段。
身份 ID/幂等键不进入模型权限决策。必要健康限制可保留可执行含义，不能为了省 token 丢掉限制。
实际 Provider input/messages 级测试验证字段和范围；规则包/模型提示不能被用户文本修改。

### 8.3 故障语义与审计

复用现有确定性处置、审核模式与 Runtime。审核不可用不能削弱已确定动作；总超时/取消/预算耗尽必须终止。
策略检查绑定实际发送载荷与最终候选版本；新快速路径不能绕过输入安全、权限、输出类型与必需审核。
诊断记录受控类别、策略版本、任务/run 标识、计数和耗时；不保存模型隐藏推理或原始敏感正文。精细业务草稿存储与诊断事件分开。
不得把“不调用写方法”宣传为数据库级权限隔离；本子项目需逐工具检查归属和允许参数，不依赖内容分类器决定能否跨用户读取。

## 9. 子项目四：任务分级与性能

简单查询走确定性数据计算；信息充分的录入走短解析/匹配路径；含糊录入走有限澄清；复杂计划走规划/校验/有限修订。范围/风险不确定不能仅为节省调用而短路。
缓存只复用确定性目录查询和已验证中间状态：键包含用户或公共数据作用域、条目/约束版本、目录版本及处理版本。用户更正、目录更新、权限变化使相关缓存失效。
不在第一版跨用户复用模型回答，不缓存权限结论，不跳过最终确认校验。按条目维护依赖，局部更正只重算受影响节点。
先对比顺序执行基线与局部复用；并行查询只用于无依赖且已授权的读取，不能为了“并行亮点”同时读取未获准模块。
首个有效反馈可用于体验指标，但“正在处理”不算任务完成；不能用流式首 token 速度代替候选可确认耗时。

## 10. 子项目五：独立评估与对照实验模块

同仓库新增独立评估包，现有 `backend/evaluation.py` 保留兼容入口，避免目录/模块同名冲突。第一版采用 CLI 和 JSON/Markdown 报告，不新建服务或数据库。
新入口默认 Mock；live 必须显式指定且具有模型调用/token/时间预算，认证凭据不进入报告。复用现有 Runtime 预算与来源记录，但每场景注入临时业务存储，禁止继承真实用户库。

### 10.1 场景与执行

场景包含 id/version、合成初始档案/目录/记录/计划、用户消息序列、预设问题应答规则、故障注入、预期允许动作/最终状态。
主要回放固定用户回答，不以另一模型扮演用户作为基础验收。面对不同提问顺序按缺失字段匹配预设答案，不能为了通过测例硬编码唯一文案。
执行器调用公开业务入口并执行确认；每场景独立临时目录/数据库/账户，串行与并行运行不共享变更状态。结束时检查记录数、版本、幂等映射和跨用户隔离。
评测产物使用合成数据；如未来允许真实用户案例，需单独授权与去标识化流程，不能自动收集线上日志作为评测集。

### 10.2 判分与指标

代码判定字段/单位/日期、硬约束、授权范围、追问修订计数、重复写入、过期恢复和版本冲突。
语气、解释质量和复杂语义由人工标注；模型可辅助但其版本和分歧必须记录，不替代确定性权限判定。

| 指标 | 定义/边界 |
| --- | --- |
| 系统处理耗时 | 各轮服务端处理耗时之和，分录入/计划、路径类型报告 P50/P95 |
| 候选可确认时间 | 首次输入到第一个通过规则校验的候选；回放自动模式不包含真实用户思考时间 |
| 用户完成时间 | 用户实验的实际起止时间，包含阅读/回答，不拿脚本耗时冒充 |
| 录入质量 | 字段准确率、人工修改率、成功保存率、追问轮数；必须报告分母和估算样本占比 |
| 计划质量 | 硬约束满足率、任务完成率、非必要变更字段数、人工修改量 |
| 安全效果 | 误拒率、风险漏检率、业务越界执行率；跨用户/确认绕过单独列确定性失败数 |
| 成本 | 每成功任务调用数/token/费用；失败与重试成本计入总成本分子，同时报告成功率 |

固定代码提交及工作区 diff 摘要、场景版本、模型标识、提示/规则/目录版本、参数、预算、时间和缓存冷热状态。禁止将 Mock 与 live 汇总成一个准确率。
对照基线为同功能同安全约束的完整顺序路径，而不是移除安全检查的“快版本”。相同场景配对比较，真实模型重复运行，报告分母与不确定性；样本过少时不夸大 P95。
上线门槛：确定性不变量测试无失败；质量/安全不得因优化退化；具体效果和延迟目标在基线测量后由用户审阅决定。此时不填写提升百分比。

## 11. 分阶段交付与依赖

| 阶段 | 交付范围 | 完成条件 |
| --- | --- | --- |
| S0 评估基础 | 隔离执行器、场景 schema、版本与指标记录、基线案例 | 默认无网络，公开入口可回放，数据不污染业务 |
| S1 安全与任务契约 | 范围/风险分轴、输入 DTO、版本确认/恢复约定 | 混合任务、数据最小化、跨用户与确认负例可验证 |
| S2 交互录入 | 多项、两轮、来源、局部更新、部分保存、恢复 UI | 关键状态与幂等场景通过；可完成端到端录入 |
| S3 计划调整 | 两领域模块、跨模块授权、两次修订、差异/版本激活 | 目标不暗改，未授权模块不变，冲突不覆盖，历史保留 |
| S4 性能对照 | 路径裁剪、依赖失效、确定性结果复用 | 配对报告显示开销变化且无质量/安全回归 |
| S5 真实模型验收 | 经批准的 live 评测、人工核查、配置灰度 | 明确费用与效果，用户批准后启用；未批准不自动运行 |

每阶段先补对应场景，再实现，再回归。S0/S1 是共享基础，不等待全部业务完工才补评估。
本文是总设计与子项目方案，不是逐文件实现计划。用户审阅后，为各阶段分别编写可执行计划，避免一次大改和跨模块同时上线。

## 12. 待审阅默认值与风险

具体建议默认值：录入草稿30天；计划会话30天/候选30分钟；联合计划整体确认；旧候选过期只能重新校验生成，不能自动生效。修订额度为整次任务共享已获确认，不再列为待定默认值。
这些建议不阻塞本设计交付，但未获确认前不能被描述为用户已经批准的产品规则。
风险：分类误判、健康限制抽取遗漏、目录份量不准确、摘要丢失约束、缓存失效不完整、存储非原子激活、模型版本变化、过度澄清影响完成率。
对应措施：保守澄清、用户确认限制、估算来源、字段契约、依赖版本、事务与幂等、评测版本固定、质量与交互耗时联合评估。仍不宣称消除所有注入或健康风险。
