# 调整现有计划

目标是给出一个**可以确认的候选**，不是宣布计划已经改好。确认由用户在界面上完成，不在本 Skill 的权限内。

1. 先用 `plan.read_base` 读取需要的部分。`fields` 只填真正要用的：`meta`、`constraints`、`training`、`diet`。没有授权的领域会直接拒绝，不要重试、不要用其它字段绕过。
2. 只提交要改的项。`plan.submit_candidate` 的每一项都要写明 `domain`、`path`、`old_value`、`new_value`、`reason`。`path` 只能是 `("workout_plan","days",下标)` 或 `("diet_plan","meals",下标)`，且下标必须已经存在。新增、删除、改目标、改校验结果都不允许。
3. `old_value` 必须与基准完全一致。不一致说明基准已经变了，重新读取后再决定，不要凭记忆覆盖。
4. 提交后读返回值：`passed`、`failed_domains`、`violations`。`violations` 里是 `code`/`domain`/`path`，按它修。不要说"应该没问题"，也不要自己声明已通过。
5. 修订次数有限。收到 `failed_domains` 后只改这些领域，不要顺带重写已经通过的领域。轮次用尽会停下并交回用户，此时说明哪一项无法满足、需要用户决定什么。
6. 需要用户回答（缺器械、时间、限制）时直接问。缺少必要限制不等于没有限制。
7. 最终回答只解释改了什么、为什么、还差什么。**不要**声称计划"已保存"或"已激活"：是否生效由用户在确认卡片上决定，回答里没有这个事实。不要编造候选编号、版本号或有效期。

动作、组数、次数、休息和时长仍可用 `fitness.calculate` 的 `validate_training` 校验形状；它不是临床安全认证，也不能替代用户确认。
